# Аудит безопасности проекта Gunfire Airsoft Clone (Раунд 2)

После исправления первичных уязвимостей был проведен повторный анализ архитектуры и кода. Выявлены следующие проблемы, касающиеся логики доступа и защиты данных.

## 🔴 Критические уязвимости (High Severity)

### 1. Отсутствие связи заказа с пользователем и IDOR (Broken Access Control)
**Компоненты:** `apps/orders/models.py`, `apps/orders/views.py`, `apps/payments/views.py`
**Описание:**
1.  Модель `Order` не содержит поля `user` (ForeignKey на модель пользователя), хотя оформление заказа (`checkout`) требует авторизации.
2.  Views просмотра заказа (`order_confirmation`) и статуса оплаты (`payment_success`, `payment_waiting`, `payment_failed`) ищут заказ только по `order_number`.
**Риск:**
Пользователь не может видеть историю своих заказов.
Любой пользователь, узнавший или подобравший номер заказа (хоть он и случайный), может просмотреть детали чужого заказа (ФИО, адрес, состав), так как нет проверки `request.user == order.user`. Это классическая уязвимость IDOR (Insecure Direct Object Reference).
**Рекомендация:**
1.  Добавить поле `user = models.ForeignKey(User, ...)` в модель `Order`.
2.  При создании заказа в `checkout` сохранять текущего пользователя.
3.  Во всех views просмотра заказа добавить проверку: если пользователь авторизован, он должен совпадать с владельцем заказа.

### 2. Отсутствие защиты от перебора паролей (No Rate Limiting)
**Компоненты:** `apps/accounts/views.py`
**Описание:**
На страницах входа (`LoginView`) отсутствуют механизмы ограничения количества попыток входа.
**Риск:**
Злоумышленник может использовать Brute Force атаку для подбора паролей пользователей.
**Рекомендация:**
Установить и настроить библиотеку `django-axes` или реализовать простую защиту на уровне Nginx/middleware.

## 🟠 Средний уровень риска (Medium Severity)

### 3. Перечисление пользователей (User Enumeration)
**Компоненты:** `apps/accounts/forms.py` (CustomUserCreationForm)
**Описание:**
При регистрации, если пользователь с таким именем/email уже существует, система явно сообщает об этом.
**Риск:**
Злоумышленник может собрать базу существующих пользователей.
**Рекомендация:**
Использовать более общие сообщения об ошибках или (как минимум) учитывать это в модели угроз. Обычно исправляется изменением логики валидации или отправкой письма "Вы пытались зарегистрироваться, но аккаунт уже есть".

## 🟡 Низкий уровень риска / Code Quality (Low Severity)

### 4. Оставленный отладочный код
**Компоненты:** `apps/cart/views.py`
**Описание:**
В коде присутствуют закомментированные вызовы `print(...)`, используемые для отладки.
**Рекомендация:**
Удалить закомментированный код для соблюдения чистоты кодовой базы.

### 5. Отсутствие валидации типов файлов
**Компоненты:** `apps/catalog/models.py`
**Описание:**
Поля `ImageField` проверяют, что файл является изображением, но дополнительные проверки (на расширение, содержимое) желательны для защиты от RCE (если загрузка доступна не доверенным лицам).
**Рекомендация:**
Использовать валидаторы для проверки расширений файлов.

---
**План действий:**
Приоритетной задачей является исправление **п.1 (IDOR и связь заказа с пользователем)**, так как это фундаментальная брешь в логике магазина.
